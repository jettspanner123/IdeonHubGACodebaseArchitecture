One login.
Every internal tool.

Four internal apps — AssetSphere, SignForge, InfraGrid, and ObservaCore — each need a login, and today that means four separate accounts, or none at all. This is the architecture for IdeonHub: a single, standards-based identity provider that any Client Application — these four and whatever comes next — redirects to, and gets a logged-in user back from.

🔐 OAuth 2.1 + PKCE 🪪 OpenID Connect 🧩 Per-App Entitlements 🚧 Standalone build — no production apps touched yet
The problem today

Four apps, four different answers to "who's logged in?"

Two apps hand-roll their own weak auth. Two apps have no auth at all. None of them know the other three exist.

SignForge

Spring Boot 3.4 · hand-rolled auth
  • JWT signed with a hardcoded secret literal in source
  • Password hashing: salted SHA-256, no key-stretching
  • Refresh token: one opaque slot per user, never rotated
  • No logout endpoint — tokens can't be revoked

AssetSphere

.NET 10 · hand-rolled auth
  • JWT signed with an env-configured HMAC secret
  • Password hashing: BCrypt — sound, but isolated to this app
  • Refresh token: same single-slot pattern as SignForge
  • Companion AI microservice has no auth at all

InfraGrid

.NET 10 · no auth exists
  • Identity today: a random per-browser client ID, for edit attribution only
  • In-code comment: "replace with real user id once auth exists"
  • No user table, no roles, nothing to migrate

ObservaCore

Node/Fastify · no auth exists
  • No user concept whatsoever — only per-device push subscriptions
  • Nav bar already has disabled "AssetSphere"/"SignForge" placeholder tabs
  • Someone already sketched a shared shell — never wired up
✕ No shared identity, anywhere, across any of the four
The shape of IdeonHub

One issuer, a registry of clients, everyone else on the outside

IdeonHub doesn't embed itself into any of the four apps' code. It sits beside them as its own service, holding its own login page and its own list of who's allowed to ask it for a token. A Client Application never sees a password — it only ever gets redirected away, and redirected back with proof. The list of clients is open-ended: these four today, more later.

Access control model

An IdeonHub account doesn't mean access to anything — yet

Logging into IdeonHub only proves who you are. Whether you can actually open AssetSphere, or InfraGrid, or any other app is a separate, explicit grant — and your role can be different in each one.

How it's provisioned

  • Admin-provisioned accounts only — no public self-registration. Someone who already knows the org's real headcount creates each account.
  • One central admin panel manages every entitlement across all four apps — not delegated per-app admins.
  • A dedicated role, IDEON_HUB_SUPER_ADMIN, independent of any app's own roles, controls that panel — including registering brand-new Client Applications.
  • Each app declares its own valid role list to IdeonHub at registration (e.g. AssetSphere declares USER, OPERATOR, ADMIN, DEVELOPER) — the admin panel shows a real dropdown, never free text.

What doesn't happen

  • No self-service sign-up, with or without email-domain gating.
  • No "access to one app implies access to another" — entitlements never cascade.
  • No real-time revocation check on every request — see below.
  • No app team self-registering its own Client Application without a super-admin.

Revocation, password reset, MFA, and the first super-admin

  • Revocation takes effect on next login/token refresh — an already-issued short-lived access token (~15 min) just runs out naturally. No real-time revocation infrastructure that every app's every request would depend on.
  • Password reset is self-service — a "Forgot password?" email flow. Admin-provisioning controls who exists; it doesn't mean routing every forgotten password through a super-admin.
  • No MFA for now, for anyone — password-only. Revisit once the four-app rollout is stable.
  • Every privileged admin action is logged — grants, revocations, role changes, new client registrations — who did it, and when.
  • The very first IDEON_HUB_SUPER_ADMIN is created by a one-time seed/bootstrap step outside the normal app. Every super-admin after that is created by an existing one, through the panel.
One protocol, four handshakes

The same trust chain, shaped to what each client can do

All four apps today are browser-based web apps — the Web App flow below is what actually matters right now. CLI, desktop, and mobile are designed for, not built for: there's no near-term plan for a non-web client, but the protocol doesn't have to be redesigned the day one shows up.

Authorization Code + PKCE

What all four apps use todayRFC 6749 §4.1 + RFC 7636
Client Application

User clicks "Sign in." The app generates a random code_verifier, derives a code_challenge (SHA-256), and redirects the browser to IdeonHub's /authorize with the challenge attached.

IdeonHub

Shows the login page. If a valid IdeonHub session cookie already exists, this step is skipped silently — that's what makes hopping between client apps feel frictionless without ever sharing a session across them.

IdeonHub

On success, redirects back to the client's registered redirect_uri with a short-lived, single-use authorization code.

Client Application

Exchanges the code plus the original code_verifier at IdeonHub's /token endpoint — server-side, never in the browser — for an access token, refresh token, and ID token.

Device Authorization Grant

No CLI client exists yetRFC 8628
Client Application

The CLI has no browser and no redirect URI to receive. It calls IdeonHub's /device_authorization endpoint directly and gets back a short user_code plus a verification URL.

Client Application

Prints: "Go to ideon.weplm.com/device and enter code WQXR-4KTL." The user does this on any other device with a browser.

Client Application

Meanwhile, the CLI polls IdeonHub's /token endpoint on an interval, asking "has this code been approved yet?"

IdeonHub

Once the user approves on the verification page, the next poll returns the access, refresh, and ID tokens directly to the CLI process.

Loopback Redirect + PKCE

No desktop client exists yetRFC 8252 §7.3
Client Application

The desktop app opens an ephemeral local port (e.g. 127.0.0.1:51204) and registers it as the redirect URI for this login attempt — IdeonHub must accept any port on loopback, since the OS assigns it at request time.

Client Application

Opens the user's system browser to IdeonHub's /authorize with a PKCE challenge, same as the web flow.

IdeonHub

After login, redirects the system browser back to http://127.0.0.1:51204/callback?code=... — landing on the desktop app's own tiny local server, not a website.

Client Application

The local listener grabs the code, exchanges it for tokens, shows "You're signed in — you can close this tab," and shuts the port down.

Custom Scheme / App Link + PKCE

No mobile client exists yetRFC 8252 §7.1–7.2
Client Application

The app registers a claimed redirect target with IdeonHub — either a custom scheme (weplm-ideonhub://callback) or, preferably, an HTTPS App Link/Universal Link it can prove it owns.

Client Application

Opens the login screen in the device's system browser or an in-app secure tab (never an embedded WebView — that can't be trusted with the password field), with a PKCE challenge attached.

IdeonHub

After login, redirects to the registered scheme or App Link, which the OS hands straight back to the mobile app.

Client Application

Exchanges the code + verifier for tokens and stores them in the platform's secure storage (Keychain / Keystore), never in plain files.

What IdeonHub actually issues

Three tokens, three jobs, none of them static

SignForge and AssetSphere both hand out one long-lived refresh token per user that's never replaced until it expires. IdeonHub rotates on every use — a stolen refresh token stops working the moment its legitimate owner refreshes again. Note: the lowercase claim names below (sub, iss, aud, exp) are OIDC/JWT-spec-mandated — PascalCase applies to IdeonHub's own custom JSON API responses, not to standard token claims, which must stay spec-compliant for any off-the-shelf OAuth/OIDC client to read them.

access_token.jwt
{
  "sub": "usr_8f2c…",
  "iss": "https://ideon.weplm.com",
  "aud": "assetsphere-web",
  "role": "OPERATOR",
  "exp": 1799999999
}
Short-lived (~15 min). Signed, stateless — never stored server-side, checked by signature + expiry alone. The role claim is scoped to the aud (that one app), not global.
refresh_token
rt_9c1f2a…d84e
  (opaque, not a JWT)

rotates: every use
reuse: revokes chain
Single-use. Each refresh issues a brand-new refresh token and invalidates the old one — reusing an old one signals theft and revokes the whole session chain.
id_token.jwt
{
  "sub": "usr_8f2c…",
  "email": "priya@theweplm.com",
  "name": "Priya Sharma",
  "amr": ["pwd"]
}
The OIDC identity token — "who logged in," for the client's own UI. Deliberately minimal (id, name, email); avatar/department ride along only when relevant, not baked in by default.
The client registry

Every Client Application is a row, not a guess

Instead of a static allowlist buried in config, each Client Application — AssetSphere, SignForge, InfraGrid, ObservaCore, tomorrow's fifth app — is a registered row IdeonHub checks on every request. A super-admin adds new clients by inserting a row, not redeploying IdeonHub.

client_id
Public identifier for the app, e.g. assetsphere-web. Sent on every authorization request.
client_type
confidential (a server that can hold a secret) or public (a browser SPA, CLI, or mobile app — can't hold a secret, must use PKCE).
redirect_uris[]
Exact allowed callback targets — a specific HTTPS URL, a loopback pattern for desktop, or a claimed custom scheme / App Link for mobile. Matched exactly, never by prefix.
declared_roles[]
Each entry is a (display label, wire value) pair — e.g. AssetSphere declares (ASSETSPHERE_ADMIN, ADMIN), (ASSETSPHERE_OPERATOR, OPERATOR). The admin panel shows the prefixed display label (disambiguates AssetSphere's ADMIN from SignForge's); the token's role claim carries only the unprefixed wire value, so the app's own code never changes. See ROLE_LABEL_MAPPING.md.
pkce_required
Always true under this design — OAuth 2.1 makes PKCE mandatory for every client type, confidential or not.
allowed_grant_types[]
Which flows this client may use — e.g. a CLI's row permits device_code, a web app's row permits authorization_code plus refresh_token.
is_active
Flip to false to instantly block new logins from a compromised or retired client — no code deploy needed anywhere.

Why this matters now

IdeonHub exists because these are live, not hypothetical

Found while researching this document, in the current production code — not IdeonHub's problem to fix directly, but exactly the pattern IdeonHub is designed to not repeat.

Critical

SignForge's application.yml has AssetSphere's real Supabase database password hardcoded as a config fallback, in a public GitHub repo.

The good news: InfraGrid and ObservaCore have zero existing auth to migrate or conflict with — both are genuine greenfield integrations for IdeonHub, not retrofits.

Do

  • Load the JWT signing key from environment/secret storage — never a source literal
  • Rotate refresh tokens on every use, and revoke the whole chain on reuse detection
  • Require PKCE on every flow, including confidential web-server clients
  • Give every client its own registry row — never a shared static secret
  • Log every privileged admin action — who, what, when

Don't

  • Store access or refresh tokens in localStorage — it's readable by any script that runs on the page
  • Reuse one long-lived refresh token indefinitely, the way both apps do today
  • Accept the Implicit or Resource Owner Password grants — both are removed under OAuth 2.1 / RFC 9700
  • Let a client redirect to anything but an exact, pre-registered URI
  • Let access to one app imply access to another
Rollout, phase by phase

IdeonHub gets built once, connected gradually

All four apps are either production (SignForge, AssetSphere) or actively used internally (InfraGrid, ObservaCore) — nothing about their login changes until IdeonHub is ready to be trusted with it.

Design

This document. Architecture, access-control model, and login page spec agreed. Nothing built yet.

Phase 1

Build IdeonHub standalone

Login page, client registry, entitlements + admin panel, /authorize · /token, JWKS + discovery doc, audit log. Zero changes to the four apps.

Phase 2

Register real clients

Add all four apps as registered clients, each declaring its own role list. Each gets a "Sign in with IdeonHub" option alongside — not replacing — its existing login (where one exists).

Phase 3

Consolidate identity

IdeonHub becomes the source of truth for user profile and role. Local user tables in SignForge and AssetSphere are migrated to reference it, then retired.
