# Prefix role labels inside IdeonHub only — never rename roles in AssetSphere or SignForge

AssetSphere's and SignForge's role names collide and look alike at a glance (both have `ADMIN`; AssetSphere also has `OPERATOR`/`USER`, SignForge has `HR_MANAGER`/`EXECUTIVE_DIRECTOR`) without actually meaning the same thing in each app. The instinct was to rename them to an app-prefixed convention (`ASSETSPHERE_ADMIN`, `SIGNFORGE_ADMIN`, etc.) everywhere, including inside AssetSphere's and SignForge's own codebases and production databases. We confirmed via direct codebase research that this would be a real, non-trivial cost in both apps: SignForge requires updating ~2 files with real role-comparison logic, 1 stray hardcoded literal, and a mandatory production `UPDATE` migration on its `role` column; AssetSphere is worse — its role strings are duplicated across 14 `[Authorize(Roles="...")]` attribute occurrences (6 controllers), 6 ad-hoc `List<string>` role-target-list occurrences (3 services), and 10+ scattered frontend literal fallbacks, none of which route through its actual `UserRoleType` enum, plus the same kind of mandatory production data migration. Neither repo has existing migration tooling to lean on.

We chose instead to keep the prefix entirely inside IdeonHub: each Client Application's registry entry stores both a **display label** (`ASSETSPHERE_ADMIN`, shown in IdeonHub's own admin panel to disambiguate at a glance) and the **wire value** (`ADMIN`, the literal string the app's own code already expects), and IdeonHub translates between them at the boundary — the access token's `role` claim always carries the wire value, so AssetSphere and SignForge never need to know the prefix exists. This gets the practical benefit (an admin looking at IdeonHub's panel can tell AssetSphere's `ADMIN` apart from SignForge's `ADMIN` at a glance) without touching either production app's code or data. The trade-off: IdeonHub's own data model carries one extra field per declared role (label vs. wire value) instead of a single string, and anyone reading IdeonHub's database directly needs to know the prefix is IdeonHub's own convention, not what AssetSphere or SignForge actually store.
