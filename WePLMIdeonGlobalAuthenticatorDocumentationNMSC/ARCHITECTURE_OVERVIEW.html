GAuth
Problem Architecture Flows Tokens Registry Security Rollout
Phase 0 · Design
WePLM Ideon · Internal Engineering Reference

One login.
Every internal tool.

Today, SignForge and AssetSphere each hand-roll their own login, their own JWT secret, and their own user table — and neither knows the other exists. This is the architecture for the Global Authenticator (GAuth): a single, standards-based identity provider that any Client Application — a web app, a CLI, a desktop app, or a mobile app — can redirect to, and get a logged-in user back from.

🔐 OAuth 2.1 + PKCE 🪪 OpenID Connect 🧩 Client Registry 🚧 Standalone build — no production apps touched yet
The problem today

Two apps, two identities, zero trust between them

SignForge and AssetSphere were built independently, on different stacks, by design. That also means every login decision was made twice — and diverged in ways that matter.

SignForge

Spring Boot 3.4 · hand-rolled auth
  • JWT signed with a hardcoded secret literal in source, not config
  • Password hashing: single-round salted SHA-256, no key-stretching
  • Refresh token: one opaque slot per user row, never rotated
  • No Spring Security — role checks are manual string comparisons per controller
  • No logout endpoint — tokens can't be revoked server-side
✕
No shared identity. No SSO. No common user record.

AssetSphere

.NET 10 · hand-rolled auth
  • JWT signed with an env-configured HMAC secret (better — still symmetric, no rotation)
  • Password hashing: BCrypt — sound, but isolated to this one app
  • Refresh token: same single-slot-per-user pattern as SignForge
  • Companion AI microservice has no authentication at all on any endpoint
  • Self-registration exists here (pending admin approval) — SignForge has none
The shape of GAuth

One issuer, a registry of clients, everyone else on the outside

GAuth doesn't embed itself into SignForge or AssetSphere's code. It sits beside them as its own service, holding its own login page and its own list of who's allowed to ask it for a token. A Client Application never sees a password — it only ever gets redirected away, and redirected back with proof.

One protocol, four handshakes

The same trust chain, shaped to what each client can do

A browser can hold a session cookie; a CLI on a headless server can't open a browser at all. OAuth 2.1 doesn't pretend these are the same problem — each client type gets the flow suited to what it can actually do, all issued from the same authorization server.

Authorization Code + PKCE

RFC 6749 §4.1 + RFC 7636
Client Application

User clicks "Sign in." The app generates a random code_verifier, derives a code_challenge (SHA-256), and redirects the browser to GAuth's /authorize with the challenge attached.

GAuth

Shows the login page. If a valid GAuth session cookie already exists, this step is skipped silently — that's what makes hopping between client apps feel frictionless without ever sharing a session across them.

GAuth

On success, redirects back to the client's registered redirect_uri with a short-lived, single-use authorization code.

Client Application

Exchanges the code plus the original code_verifier at GAuth's /token endpoint — server-side, never in the browser — for an access token, refresh token, and ID token.

Device Authorization Grant

RFC 8628
Client Application

The CLI has no browser and no redirect URI to receive. It calls GAuth's /device_authorization endpoint directly and gets back a short user_code plus a verification URL.

Client Application

Prints: "Go to gauth.weplm.com/device and enter code WQXR-4KTL." The user does this on any other device with a browser.

Client Application

Meanwhile, the CLI polls GAuth's /token endpoint on an interval, asking "has this code been approved yet?"

GAuth

Once the user approves on the verification page, the next poll returns the access, refresh, and ID tokens directly to the CLI process.

Loopback Redirect + PKCE

RFC 8252 §7.3
Client Application

The desktop app opens an ephemeral local port (e.g. 127.0.0.1:51204) and registers it as the redirect URI for this login attempt — GAuth must accept any port on loopback, since the OS assigns it at request time.

Client Application

Opens the user's system browser to GAuth's /authorize with a PKCE challenge, same as the web flow.

GAuth

After login, redirects the system browser back to http://127.0.0.1:51204/callback?code=... — landing on the desktop app's own tiny local server, not a website.

Client Application

The local listener grabs the code, exchanges it for tokens, shows "You're signed in — you can close this tab," and shuts the port down.

Custom Scheme / App Link + PKCE

RFC 8252 §7.1–7.2
Client Application

The app registers a claimed redirect target with GAuth — either a custom scheme (weplm-authenticator://callback) or, preferably, an HTTPS App Link/Universal Link it can prove it owns.

Client Application

Opens the login screen in the device's system browser or an in-app secure tab (never an embedded WebView — that can't be trusted with the password field), with a PKCE challenge attached.

GAuth

After login, redirects to the registered scheme or App Link, which the OS hands straight back to the mobile app.

Client Application

Exchanges the code + verifier for tokens and stores them in the platform's secure storage (Keychain / Keystore), never in plain files.

What GAuth actually issues

Three tokens, three jobs, none of them static

SignForge and AssetSphere both hand out one long-lived refresh token per user that's never replaced until it expires. GAuth rotates on every use — a stolen refresh token stops working the moment its legitimate owner refreshes again.

access_token.jwt
{
  "sub": "usr_8f2c…",
  "iss": "https://gauth.weplm.com",
  "aud": "signforge-web",
  "role": "HR_MANAGER",
  "exp": 1799999999
}
Short-lived (~15 min). Signed, stateless — never stored server-side, checked by signature + expiry alone.
refresh_token
rt_9c1f2a…d84e
  (opaque, not a JWT)

rotates: every use
reuse: revokes chain
Single-use. Each refresh issues a brand-new refresh token and invalidates the old one — reusing an old one signals theft and revokes the whole session chain.
id_token.jwt
{
  "sub": "usr_8f2c…",
  "email": "priya@theweplm.com",
  "name": "Priya Sharma",
  "amr": ["pwd"]
}
The OIDC identity token — "who logged in," for the client's own UI. Never sent to APIs as an authorization credential; the access token does that job.
The client registry

Every Client Application is a row, not a guess

Instead of a static allowlist buried in config, each Client Application — SignForge's web app, AssetSphere's web app, tomorrow's CLI — is a registered row GAuth checks on every request. New clients get added by inserting a row, not redeploying GAuth.

client_id
Public identifier for the app, e.g. signforge-web. Sent on every authorization request.
client_type
confidential (a server that can hold a secret) or public (a browser SPA, CLI, or mobile app — can't hold a secret, must use PKCE).
redirect_uris[]
Exact allowed callback targets — a specific HTTPS URL, a loopback pattern for desktop, or a claimed custom scheme / App Link for mobile. Matched exactly, never by prefix.
pkce_required
Always true under this design — OAuth 2.1 makes PKCE mandatory for every client type, confidential or not.
allowed_grant_types[]
Which flows this client may use — e.g. a CLI's row permits device_code, a web app's row permits authorization_code plus refresh_token.
is_active
Flip to false to instantly revoke a compromised or retired client — no code deploy needed anywhere.
Why this matters now

GAuth exists because these are live, not hypothetical

Found while researching this document, in the current production code — not GAuth's problem to fix directly, but exactly the pattern GAuth is designed to not repeat.

Critical

SignForge's application.yml has AssetSphere's real Supabase database password hardcoded as a config fallback, in a public GitHub repo.

SignForgeOrchestratorServiceLayerMSC/src/main/resources/application.yml:42
High

SignForge's JWT signing secret is a hardcoded string literal in source code, not an environment variable — anyone with repo read access can forge valid tokens.

JwtTokenHelper.java — DEFAULT_SECRET
High

AssetSphere's AI microservice has no authentication guard on any endpoint, despite a Swagger annotation implying one exists.

AssetsphereAIServiceLayerMSC — no AuthGuard found

Do

  • Load the JWT signing key from environment/secret storage — never a source literal
  • Rotate refresh tokens on every use, and revoke the whole chain on reuse detection
  • Require PKCE on every flow, including confidential web-server clients
  • Give every client its own registry row — never a shared static secret

Don't

  • Store access or refresh tokens in localStorage — it's readable by any script that runs on the page
  • Reuse one long-lived refresh token indefinitely, the way both apps do today
  • Accept the Implicit or Resource Owner Password grants — both are removed under OAuth 2.1 / RFC 9700
  • Let a client redirect to anything but an exact, pre-registered URI
Rollout, phase by phase

GAuth gets built once, connected gradually

SignForge and AssetSphere are production apps — nothing about their login changes until GAuth is ready to be trusted with it.

Design

This document. Architecture agreed, nothing built yet.

Phase 1

Build GAuth standalone

Login page, client registry, /authorize · /token · /device_authorization, JWKS + discovery doc. Zero changes to SignForge or AssetSphere.

Phase 2

Register real clients

Add SignForge and AssetSphere as registered clients. Each gets a "Sign in with GAuth" option alongside — not replacing — its existing login.

Phase 3

Consolidate identity

GAuth becomes the source of truth for user profile and role. Local user tables in SignForge and AssetSphere are migrated to reference it, then retired.
