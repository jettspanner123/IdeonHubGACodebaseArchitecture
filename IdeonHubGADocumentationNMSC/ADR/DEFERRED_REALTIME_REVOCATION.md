# Deferred revocation instead of real-time checks

When an `IDEON_HUB_SUPER_ADMIN` revokes a user's access to an app (or deactivates their account entirely), IdeonHub does not cut that access off within seconds. Instead, revocation blocks future logins and token refreshes immediately, but any access token already issued keeps working until it naturally expires (short-lived, on the order of minutes). The alternative — real-time revocation — would require every Client Application's backend to check revocation status against IdeonHub on every single request, not just at login, turning IdeonHub into a dependency every app's every request routes through. We chose deferred revocation because a short-lived access token already bounds the damage tightly, and "an employee left the company" is rarely, if ever, time-critical to the second. This means a revoked user can retain working access to an app for up to one token lifetime after revocation — acceptable given the token lifetime is deliberately kept short, but worth knowing if a future incident ever needs access cut off faster than that.
